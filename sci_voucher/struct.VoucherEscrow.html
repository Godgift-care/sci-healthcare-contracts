pub fn create_voucher( env: Env, funder: Address, beneficiary_ref: BytesN<32>, provider: Address, service_code: u32, amount: i128, expires_at: u64, ) -> Result<u64, VoucherError>

Escrows amount against one service at one active provider.

The funder need not be the patient. A relative sending from abroad funds a voucher exactly the same way, which is the point: this is a remittance that can only be spent on the care it was sent for.

The registry price is read when this call executes. A client that showed a price before signing should use create_voucher_at_price instead, so a price change in between cannot silently apply.

pub fn create_voucher_at_price( env: Env, funder: Address, beneficiary_ref: BytesN<32>, provider: Address, service_code: u32, amount: i128, expires_at: u64, expected_price: i128, ) -> Result<u64, VoucherError>

Escrows amount only if the registry still lists expected_price.

Use this when a price was shown to the funder before they signed: if the clinic changed the price between the quote and this call, the call fails with PriceChanged and nothing is escrowed. create_voucher keeps reading the current price for callers that do not care.

pub fn create_voucher_with_options( env: Env, funder: Address, beneficiary_ref: BytesN<32>, provider: Address, service_code: u32, amount: i128, expires_at: u64, options: VoucherOptions, ) -> Result<u64, VoucherError>

create_voucher with optional terms chosen by the funder:

  • presence_commitment: SHA-256 of a secret the funder gives the patient. The clinic must then claim with claim_with_proof, revealing the secret, so a claim shows the clinic had the patient rather than only saying so.
  • dispute_window: a dispute window for this voucher, within the bounds (InvalidDisputeWindow otherwise). A funder of expensive care can take longer to object; a small voucher can settle sooner.

A voucher whose amount is above get_presence_threshold() must set presence_commitment (PresenceCommitmentRequired otherwise). With the threshold at 0, the protocol imposes no requirement.

With both options unset and no threshold, this is exactly create_voucher.

pub fn reduce_amount( env: Env, funder: Address, voucher_id: u64, new_amount: i128, ) -> Result<(), VoucherError>

Gives back an overpayment without giving up the voucher.

A funder who paid more than the listed price can bring the escrowed amount down to the service price and keep the voucher. The difference goes straight back to the funder, and no fee is taken on money that never became care.

The floor is the price the registry lists at call time, so a clinic that has raised its price cannot have a funded voucher reduced below that price, and a clinic that has lowered it frees the funder to reduce further. Only a Funded voucher can be reduced: once the clinic has claimed it, the escrowed amount is what the clinic is expecting to be paid.

Errors:

  • NotAuthorized — the caller is not the voucher’s funder.
  • InvalidStatus — the voucher is no longer Funded.
  • InvalidAmount — new_amount is not positive.
  • AmountNotReduced — new_amount is not below the escrowed amount.
  • ServiceNotOffered — the service is no longer listed, so there is no price to reduce towards.
  • AmountBelowPrice — new_amount is below the current listed price.

pub fn claim( env: Env, provider: Address, voucher_id: u64, ) -> Result<(), VoucherError>

Provider marks the patient as presented and the service as begun.

A provider suspended after the voucher was funded cannot claim it; the voucher can be refunded at once instead of waiting for expiry. A voucher funded with a presence commitment is refused (PresenceProofRequired): it is claimed with claim_with_proof.

pub fn claim_with_proof( env: Env, provider: Address, voucher_id: u64, secret: Bytes, ) -> Result<(), VoucherError>

Claims a voucher funded with a presence commitment by revealing the secret behind it. sha256(secret) must equal the commitment (InvalidPresenceProof otherwise); a voucher without one is NoPresenceCommitment.

The secret becomes public on chain with this call. That is harmless: it was only ever good for this one voucher, which this claim uses up.

pub fn attest( env: Env, attester: Address, voucher_id: u64, ) -> Result<(), VoucherError>

Only a registry attester may call this — deliberately not the provider being paid. Separating the party who gets paid from the party who confirms delivery is the main check in this protocol.

pub fn settle(env: Env, voucher_id: u64) -> Result<(), VoucherError>

Source

pub fn refund(env: Env, voucher_id: u64) -> Result<(), VoucherError>

Returns escrow to the funder when care can no longer happen.

  • A Funded voucher is refundable once it expires unclaimed, or immediately if its provider is no longer active in the registry. A clinic suspended after the voucher was funded cannot serve it, so the funder should not have to wait for expiry.
  • A Claimed voucher that was never attested is refundable once CLAIM_GRACE_SECS have passed after expiry, so a claim alone can never lock the funder’s money forever. Suspension does not shorten this path: care may already have been given before the clinic was suspended, and an attester may still confirm it.

Permissionless for the same reason as settle.

Source

pub fn resolve_dispute( env: Env, admin: Address, voucher_id: u64, refund_funder: bool, ) -> Result<(), VoucherError>

Admin resolves a dispute. refund_funder picks the winner.

This is the protocol’s honest weak point and it is not hidden: resolution is a trusted human decision. It is scoped as narrowly as possible — the admin can only route already-escrowed funds to one of the two parties, and can never divert them elsewhere.

Source

pub fn resolve_split( env: Env, admin: Address, voucher_id: u64, to_provider: i128, ) -> Result<(), VoucherError>

Admin resolves a dispute by splitting the escrow between the parties.

to_provider is the gross part of the voucher awarded to the clinic, from 0 to the voucher amount. The clinic receives to_provider minus the protocol fee on that part, the fee account receives the fee, and the funder receives the rest. The three amounts add up to the voucher amount exactly, whatever to_provider is.

A split of 0 is a full refund and a split of the whole amount is a full payout; in between, the voucher ends Settled because some care was paid for. A care receipt is minted only when the clinic receives something, so no receipt exists for a split that refunds everything.

Like resolve_dispute, this is a trusted admin decision, but it can still route escrow only to the clinic, the fee account and the funder.

pub fn escrow_summary(env: Env) -> Result<(i128, i128), VoucherError>

Read-only solvency check: (open_escrow, token_balance).

open_escrow is the running total of amounts belonging to vouchers that have been funded and not yet settled or refunded. token_balance is the contract’s actual balance of the settlement token. The two are equal when the accounting is correct; anything else is a bug or tokens sent to the contract outside a voucher.

No authorisation: anyone may run the check.

pub(crate) fn ensure_escrow_covers( env: &Env, token_client: &Client<'_>, amount: i128, ) -> Result<(), VoucherError>

Fails with EscrowShortfall when the contract holds less of the token than amount.

Escrow is one token balance shared by every open voucher, so this can only happen if the issuer clawed funds back from the contract. Checking first turns what would be a host panic deep inside the token into a defined error, and the whole invocation reverts: nothing is half-paid.

Source

pub(crate) fn receive( env: &Env, token_client: &Client<'_>, from: &Address, amount: i128, ) -> Result<(), VoucherError>

Pulls amount from from into escrow and checks the escrow balance rose by exactly amount.

Every voucher’s escrow is one shared token balance, and open_escrow counts what was requested. A token that skims a transfer fee or runs a hook that redirects part of it would otherwise leave the voucher recording more than the contract holds, and the shortfall would land silently on whichever voucher pays out last. Measuring the balance makes such a token fail closed with TokenAmountMismatch instead.

Source

pub(crate) fn send( env: &Env, token_client: &Client<'_>, to: &Address, amount: i128, ) -> Result<(), VoucherError>

Moves amount out of escrow, turning a refused transfer — a frozen (deauthorized) escrow or recipient — into TokenTransferFailed.

It then checks the escrow fell by exactly amount (a token that debits more would eat into other vouchers’ escrow) and the recipient rose by exactly amount (a token that delivers less would short the clinic, attester or funder). Either mismatch is TokenAmountMismatch.

Source

pub(crate) fn require_moved( before: i128, after: i128, amount: i128, ) -> Result<(), VoucherError>

TokenAmountMismatch unless after - before == amount.

pub(crate) fn pay_out( env: &Env, config: &Config, voucher: &mut Voucher, ) -> Result<(), VoucherError>

Pays the provider, splits the fee between the attester and the fee account, and mints the care receipt.

Config guarantees attester_share_bps <= fee_bps, so the attester share can never exceed the fee and the three payouts always sum to the voucher amount exactly:

net             = amount - fee
attester_share  = amount * attester_share_bps / 10_000
fee_account     = fee - attester_share

A voucher attested before attesters were stored has no attester to pay, so the whole fee goes to the fee account, as it did before.

Source

pub(crate) fn pay_split( env: &Env, config: &Config, voucher: &mut Voucher, to_provider: i128, fee: i128, to_funder: i128, ) -> Result<(), VoucherError>

Pays a resolved dispute in parts: to_provider gross to the clinic (minus its fee), the fee to the fee account and to_funder back to the funder. The caller has already checked that the parts add up.

Source

pub(crate) fn pay_back( env: &Env, config: &Config, voucher: &mut Voucher, ) -> Result<(), VoucherError>

Returns the full escrowed amount to the funder. No fee is taken on care that never happened.

The three amounts add up to the voucher amount exactly, whatever to_provider is.

A split of 0 is a full refund and a split of the whole amount is a full payout; in between, the voucher ends Settled because some care was paid for. A care receipt is minted only when the clinic receives something, so no receipt exists for a split that refunds everything.

Like resolve_dispute, this is a trusted admin decision, but it can still route escrow only to the clinic, the fee account and the funder.
