### Changed
- **registry:** `set_provider_status` now refuses `reason_code` 0 with the new `MissingReasonCode` (#16). Code 0 means "no status change yet" and is written only by registration, so every admin change, and above all reinstating a suspended clinic (`Suspended → Active`), must record a real reason. Tests now cover every caller of reinstatement (the clinic itself, a stranger, an attester, another clinic, a nominated admin before `accept_admin`, a previous admin after handover, and the admin's address without its signature), and each refusal leaves the clinic suspended with its suspension reason intact. Authorisation is still checked first. **Integrators:** a script that passes `--reason_code 0` now fails. The repository's scripts and examples already pass `1` (verified). Closes #302.
- **registry:** `register_provider` now accepts a country only in the shape of an ISO 3166-1 alpha-2 code: exactly two ASCII uppercase letters. `ng`, `N1`, two spaces and multi-byte characters that happen to occupy two bytes are refused with the existing `InvalidCountry`, so `ng` and `NG` can no longer register as two different countries and junk codes cannot break the app's or indexer's country filter. Checking a code against the full ISO list stays an off-chain concern. Closes #23.
- **registry:** `set_provider_status` rejects status changes that carry no information. Only `Pending → Active`, `Pending → Suspended`, `Active → Suspended` and `Suspended → Active` are accepted; everything else — setting the same status twice, the backwards `Active → Pending`, and any move into or out of `Retired` — fails with the new `InvalidTransition` (#14), so the event history the indexer and auditors read contains no no-op or unexplained entries. See the [status lifecycle](docs/developers/contracts.md#status-lifecycle) for the full transition table. Closes #25.

It covers creating the funder account separately from the protocol admin, the trustline and fee float, a table of every funder action with its required signatures — `create_voucher`, `create_voucher_with_options`, `reduce_amount`, `redirect` and `dispute` need two, while `refund` is permissionless — proof that refunds and reductions return to the stored funder address, a per-voucher record-keeping and reconciliation template, and a testnet walkthrough. Linked from the funder guide, the multisig admin guide, the docs index and the README. Closes #307.
- **registry:** `providers_in(country, start, limit)` looks up active clinics by country without an indexer. `register_provider` seeds a per-country count, `set_provider_status` adds a clinic to its country's index when it becomes `Active` and removes it (swap-and-pop) when it stops being `Active`, and `providers_in` pages the result with `limit` capped at `MAX_PROVIDERS_PAGE`. Closes #34.
- **registry:** every status change now records **why**. `set_provider_status` takes a `reason_code: u32`, stored on the provider (field `reason_code`, `0` at registration) and published in `provider_status_changed` (data `status`, `reason_code`), so a suspended clinic knows what to fix and funders can tell a fraud suspension from expired paperwork. The codes — 1 verified, 2 documents expired, 3 complaint under review, 4 fraud, 5 closed — are documented in [the trust model](docs/protocol/trust.md#reason-codes) and are added, never renumbered. **Indexer follow-up:** `provider_status_changed` gains a `reason_code` data field, read by name, so `sci-healthcare-backend` needs no decoder change to keep working; open a backend/frontend issue to surface it. Closes #24.
- **registry:** a clinic can leave the registry itself. `retire(owner, reason_code)` — signed by the clinic's owner only — sets the new terminal `Retired` status. A retired clinic is not an active provider, so `voucher` refuses to fund it any new vouchers; vouchers already funded against it refund as they always could (immediately, before expiry) and a voucher claimed while the clinic was active still attests and settles as care delivered. The admin cannot move a clinic into `Retired` (that is `InvalidTransition`, #14) and cannot bring one out: the way back is to register again. Emits `provider_status_changed` with `status = Retired`, so indexers need no new event to track departures; `is_active_provider` already returns `false`, so `create_voucher` rejects retired clinics without a change to the voucher contract. Closes #26.
- **receipt:** `provider_stats(provider)` returns `(count, total_amount)` — a clinic's on-chain track record, readable by anyone without an indexer. `mint` now maintains both counters per provider: the existing `ProviderCount(provider)` index length, and a new `ProviderTotal(provider)` running total of the amounts, both kept with overflow-checked arithmetic so a count or total that would wrap is refused with the new `MathOverflow` (#9) instead of understating what a clinic was paid. Both entries are TTL-extended on `provider_stats` reads like every other persistent entry, and a provider with no receipts reports `(0, 0)`. Closes #57.
- **voucher:** `redirect(funder, voucher_id, new_provider)` lets the funder move a still-`Funded` voucher to another active clinic that offers the same service at a price no higher than the escrowed amount, provided the service is available. The amount, expiry and escrow do not change. `voucher_redirected` records the funder and new clinic as topics, with the previous clinic, voucher id and service code in its data; indexers should add `voucher_redirected: ['funder', 'new_provider']` to `TOPIC_FIELDS` in `sci-healthcare-backend/src/stellar/events.ts`. Closes #40.
- **voucher:** `decline(provider, voucher_id, reason_code)` lets a clinic immediately return a `Funded` voucher it cannot provide. Only the voucher's provider may call it; the full amount goes back to the funder without a fee and open escrow decreases. It emits `voucher_declined` (topic `provider`; data `voucher_id`, `reason_code`, `service_code`, `amount`) as well as the existing `voucher_refunded` event. The separate indexer needs `voucher_declined: ['provider']` in `TOPIC_FIELDS` in `sci-healthcare-backend/src/stellar/events.ts`. Closes #41.
- **voucher:** `reduce_amount(funder, voucher_id, new_amount)` lets a funder recover an overpayment without giving up the voucher. While the voucher is still `Funded`, the escrowed amount can be brought down to the clinic's listed price — never below it — and the difference goes straight back to the funder, with no fee taken on money that never became care. The floor is the price the registry lists **at call time**: a raised price cannot be undercut, and a lowered price frees the funder to reduce further. A voucher whose service has been delisted cannot be reduced (there is no price to reduce towards) and is refunded at expiry instead, and a claimed voucher cannot be reduced at all — the amount is what the clinic expects to be paid. The difference leaves escrow, so the running `open_escrow` total reported by `escrow_summary` follows it down. The new `voucher_amount_reduced` event (topics `funder`; data `voucher_id`, `service_code`, `previous_amount`, `amount`, `refunded`) needs one line in the indexer: `voucher_amount_reduced: ['funder']` in `TOPIC_FIELDS` in `sci-healthcare-backend/src/stellar/events.ts`. Its data fields are read by name and need no decoder change; until the line is added the event still decodes, but its `funder` topic reads as `undefined`. The new `AmountNotReduced` error is #22. Closes #89.
- **voucher:** settlement now pays the attester a configurable share of the protocol fee. `Config` gains `attester_share_bps`, set once at initialisation and bounded by `fee_bps` (the new `InvalidAttesterShare`, #21, rejects a larger share), so the attester share is carved out of the fee and never charged on top of the clinic's net. `attest` stores the attester on the voucher, and `settle` pays the clinic `amount - fee`, the attester `amount * attester_share_bps / 10_000`, and the fee account the remainder; the three amounts sum to the voucher exactly. A share of 0 reproduces today's payout, and a dispute resolved for the provider without an attestation has no attester of record, so the fee account keeps the whole fee. `scripts/deploy.sh` defaults to 50 bps (half of the 1% fee) and accepts an `ATTESTER_SHARE_BPS` override. Economics docs, the contract reference and the attester guide are updated, with settlement tests for a non-zero share, a zero share, a full-fee share and the configured bound.
- **voucher:** `create_voucher_at_price(funder, beneficiary_ref, provider, service_code, amount, expires_at, expected_price)` escrows only when the registry price still equals `expected_price`, and otherwise fails with the new `PriceChanged` (#23) before any token moves. This closes the race between showing a funder a quote and applying their signed transaction, including a price change in either direction. `create_voucher` is unchanged and still reads the current price for callers that do not show a quote first. No event layout changed. Closes #135.
- **registry:** `schedule_service_price` now takes `confirm_large_change`. A scheduled price of `MAX_PRICE_JUMP` (5) times the current price or more is rejected with the new `LargePriceJumpNeedsConfirmation` (#14) unless the caller passes `true`, so a mistyped zero cannot overcharge every funder that day. A smaller rise, a cut, or scheduling the current price to call a change off needs no flag; the 24-hour notice still applies. `upsert_service` still refuses to raise a price, so the guard sits on the only path that can. Closes #133.

### Changed
- **voucher:** each voucher is stored positionally — an XDR vec of its values, without the id that is already its key — instead of as a named struct, whose XDR map carries every field name in every entry. For an attested voucher the stored value drops from 464 to 228 bytes, about half, and persistent rent is charged on entry size. Options a funder sets live in a separate entry written only when used. `get_voucher` and every other function take and return the same `Voucher` as before; no behaviour changes. The voucher contract has no upgrade entry point, so there is no stored data in the old layout to migrate. Closes #124.
- **voucher:** `voucher_settled` gains `attester_share` (the part of `fee` paid to the attester), appended after the existing fields. Topics are unchanged and the data map is keyed by name, so decoders that read by field name pick it up without a breaking change. `attester_share + (fee - attester_share) == fee`, and `net + fee == amount` still holds.
- **registry:** `schedule_service_price` gains a sixth argument, `confirm_large_change: bool`. Callers that schedule an ordinary rise, a cut, or a cancellation pass `false`; a rise to 5× the current price or more needs `true` (see Added). Existing integrations that call the four-argument form must add the argument before their next deployment. The emitted `service_price_scheduled` event is unchanged.
- **receipt:** `set_minter(admin, minter)` is replaced by `propose_minter` / `accept_minter` (see Added). `scripts/deploy.sh` now initialises the receipt book with the voucher contract as minter directly, because both instances are deployed before either is initialised; later changes go through the two-step handover.
- **voucher:** `quote` and `settle` are covered by a lifecycle test for a range of amounts, including the rounding cases and the largest fundable amount, so a quote shown before signing is proven to match what settlement pays. (#108)
- **voucher:** `voucher_attested` carries `remaining_today`, appended after the existing fields: the attestations that attester has left today. Topics are unchanged and the data map is keyed by name, so decoders that read by field name pick it up without a breaking change. (#100)
- **registry:** `upsert_service` no longer raises the price of an existing service; it returns `PriceIncreaseNeedsNotice` (#13) and the rise goes through `schedule_service_price`. Listing a new service and lowering a price still apply at once. `ServiceItem` gains `pending_price` and `effective_at`. (#99)
- **receipt:** `count_for` now extends the TTL of the count entry it reads. It was the only persistent read in the three contracts that did not, so a patient's episode count could be archived while their receipts stayed live. Covered by `count_for_extends_its_own_entry`.
- **scripts:** `scripts/deploy.sh` now refuses to overwrite an existing `deployments/<network>.env` unless `--force` is passed, so an accidental second run cannot replace the live addresses. `--dry-run` prints every command without building, deploying or sending a transaction, and the final summary makes the outcome explicit. `scripts/test-deploy.sh` covers the refusal, `--force` and dry-run paths without a network, and the new `deploy script` CI job runs it on every pull request.
- **deploy:** `scripts/deploy.sh` and `scripts/deploy-faucet.sh` deploy the wasm that `scripts/build-wasm.sh` produces, so what is deployed is what is released. The faucet used to be built on its own (`cargo build -p sci-faucet`), which links a different `soroban-sdk` than the rest of the workspace and produces different bytes.
- **build:** the build takes the cargo registry path out of the wasm (`--remap-path-prefix`). The Soroban SDK embeds the absolute path of its own source in its panic messages, so the artefact used to carry the builder's home directory, and two machines never agreed on its hash.
- **cargo:** the workspace path dependencies carry a version, so `cargo deny` does not read them as wildcard version requirements.
- **voucher:** `voucher_claimed`, `voucher_attested`, `voucher_disputed`, `voucher_settled` and `voucher_refunded` now carry `service_code` and `amount` in their data, appended after the fields each event already had. Only `voucher_created` used to say what the voucher was for, so an indexer or wallet reading a single lifecycle event had to load the voucher to show what was paid for. `voucher_refunded` already carried `amount`; it gains `service_code` only. Topics are unchanged and the data map is keyed by name, so the indexer in `sci-healthcare-backend` decodes the new layout without a breaking change (its matching decoder change is linked from the pull request). Covered by five event snapshot tests in `contracts/voucher/src/test.rs` that read the decoded XDR event and the regenerated `test_snapshots`.
